# Face embedding — эмбеддинг лиц (планируемая модель)

## Общая информация

**Face embedding** — задача получения векторного представления (эмбеддинга) лица для последующего сопоставления/ре-идентификации. В стеке CARS это **планируемая (to-be-trained) задача, конкретная модель ещё не выбрана и не существует**. Соответствующая строка в `models.md` оставлена пустой:

```
Task           | model name | URL  | version    | Local path
Face embedding | None       | None | Trainable
```

То есть для этой задачи **нет имени модели, нет URL, нет версии, нет весов и не выбрана архитектура**. Документ описывает задачу-задел на будущее, а не реальный артефакт. Везде, где приводится «типовой» подход, это явно помечено как *предположение / TBD* и не должно трактоваться как факт о существующей модели.

> **Не путать с FaceDetect.** Face embedding — это **отдельная** downstream-модель относительно детектора лиц **FaceDetect** (NVIDIA FaceNet `pruned_quantized_v2.0.1`, см. строку «Face Detector» в `models.md`; локальный путь модели `home/mk/Загрузки/CarCVModels/facenet_pruned_quantized_v2.0.1`). FaceDetect **детектирует** bbox лиц; задача эмбеддинга — превратить выровненный кроп лица в вектор для сравнения. Спека детектора (`docs/about_models/facedetect.md`) на момент создания этого документа в репозитории ещё не оформлена.

## Архитектура

**Не определена.** Архитектура, backbone, pruning/quantization — всё TBD, так как модель не выбрана.

Типовой (предположительный, **не подтверждённый**) подход для задачи эмбеддинга лиц:

- семейства **ArcFace / CosFace / FaceNet-embedding** поверх CNN-backbone (например ResNet/MobileFaceNet);
- обучение с metric-learning лоссом (angular margin / triplet);
- выход — L2-нормированный вектор фиксированной размерности.

Любые из перечисленных вариантов — иллюстрация типового решения, а **не** выбор для CARS. Конкретное семейство будет зафиксировано при появлении модели.

## Использование для CarCV

Предполагаемое (но **не реализованное**) назначение — построение эмбеддингов лиц водителя/пассажиров поверх кропов, выдаваемых детектором FaceDetect, для ре-идентификации и сопоставления лиц между кадрами/сессиями. Это задел на будущее; в текущем стеке задача не закрыта.

### Применимость

- ✅ (потенциально, в будущем) Ре-идентификация / сопоставление лиц 1:1 (верификация) и 1:N (идентификация) поверх кропов FaceDetect — **после** выбора и обучения модели.
- ✅ (потенциально) Отдельный downstream-модуль, не пересекающийся с детекцией: вход — готовый кроп лица.

### Ограничения

- ❌ **Модели не существует.** Нет весов, архитектуры, версии — реализовать или измерить нечего.
- ❌ **Нет пригодного датасета с identity-метками.** В `datasets.md` строка Face embedding привязана к **WIDER FACE**, но WIDER FACE — **детекционный** датасет **без меток идентичности персон** и для обучения/оценки эмбеддинга **непригоден**. Это прямо отмечено в спеке датасета (`docs/about_datasets/wider_face.md`): в разделах «Использование для CarCV» и «Ограничения» указано, что датасет не содержит меток идентичности персон и для эмбеддинга непригоден (дословная формулировка «Нет меток идентичности персон → датасет не подходит для обучения/оценки будущей модели эмбеддинга лиц» — в разделе «Ограничения», строка 168).
- ⚠️ Понадобится **отдельный датасет с identity-метками** (тип LFW / MS-Celeb / собственный сбор лиц водителей) — когда задача дойдёт до реализации.
- ⚠️ **Domain gap (предположительно):** automotive POV (лицо через лобовое стекло, дистанция 5–50 м, day/night/IR) сильно отличается от типовых лицевых датасетов; качество эмбеддинга в этих условиях не оценено.

### Рекомендации

1. **Не валидировать сейчас.** Задача исключена из охвата валидационной кампании — измерять нечего (модель отсутствует полностью: в `models.md` `None`, нет даже имени, в отличие от Color, где указано `bae_model_f3`, но задача тоже вне охвата).
2. **Зафиксировать выбор модели** прежде всего: семейство (ArcFace/CosFace/FaceNet-embedding или иное), размер входа, размерность вектора, лицензия весов. Только после этого имеет смысл оформлять полноценную спеку и препроцессинг.
3. **Не использовать WIDER FACE для эмбеддинга.** Заменить привязку датасета: подобрать набор с метками идентичности персон (LFW/MS-Celeb-подобный или собственный сбор), пригодный для метрик верификации/идентификации.
4. **Определить метрики качества** под задачу (типично — **TAR@FAR**, верификация 1:1, идентификация 1:N) и пороги pass/fail заранее, по образцу остальных моделей кампании.
5. **Согласовать privacy/legal** при сборе и хранении лиц (биометрические данные) до начала обучения коммерческой модели.

## Валидация

**Не проводилась — модель отсутствует полностью.** Задача **исключена из охвата** валидационной кампании наряду с Color (тоже вне охвата): в дизайне кампании прямо указано «Face embedding — нет модели (`Trainable`)» (см. `docs/superpowers/specs/2026-06-02-validation-campaign-5-models-design.md`, раздел «Охват: модель × датасет»). Отличие статусов: у Face embedding в `models.md` стоит `None` (нет даже имени), тогда как у Color указано имя `bae_model_f3` (пусты только URL/версия) — но обе задачи в текущую кампанию не входят. Порогов pass/fail нет, измеренного результата нет.

Привязка датасета в `datasets.md` (Face embedding → WIDER FACE) **некорректна для этой задачи**: WIDER FACE — детекционный бенчмарк без идентичностей. Подробности и обоснование непригодности — в спеке датасета: [wider_face.md](../about_datasets/wider_face.md). Для будущей валидации эмбеддинга понадобится отдельный датасет с identity-метками.

> Этот же WIDER FACE по согласованию используется для валидации **детектора** FaceDetect (а не эмбеддинга) — см. примечание в дизайне кампании.
